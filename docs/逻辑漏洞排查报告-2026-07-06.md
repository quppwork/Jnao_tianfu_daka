## P0 — DB 异常时认证完全绕过

**文件:** [backend/app/core/deps.py#L46-L51](../backend/app/core/deps.py#L46-L51)

**严重度:** 🔴 高危（安全漏洞）

```python
def get_authenticated_user(...):
    uid = user_id or x_child_user_id
    ...
    try:
        user = db.get(ChildUser, uid)
    except Exception:              # ← 捕获一切异常
        logger.warning("...降级为无 token 验证")
        return uid                 # ← 直接放行，零认证
```

**问题分析:**

注释标注为 `session_token 列可能还不存在` 的迁移兼容逻辑，但 `except Exception` 捕获范围过宽：

- 连接池耗尽
- 数据库死锁
- 网络抖动
- 表不存在
- 任何其他 DB 异常

以上全部会静默跳过认证，返回未验证的 `uid`。

**影响:**

生产环境中一旦 DB 出现抖动，所有需要认证的 API 端点全部放行，攻击者可伪造任意 `user_id` 访问其他用户数据。

**日志证据:**

```
2026-07-06 17:21:13 [WARNING] get_authenticated_user: DB 查询失败
（session_token 列可能未创建），降级为无 token 验证
```

**修复方案:**

```python
except Exception as e:
    # 仅对列不存在的特定异常做降级
    if "no such column" in str(e) or "Unknown column" in str(e):
        logger.warning("session_token 列未创建，降级处理")
        return uid
    raise  # 其他异常向上抛出
```

**修复难度:** 低（缩小异常范围，约 3 行改动）

## P1 — 过期方案未清理，同天产生多条脏记录

**文件:**
- [backend/app/services/training_service.py#L117-L131](../backend/app/services/training_service.py#L117-L131)
- [backend/app/services/training_service.py#L180-L188](../backend/app/services/training_service.py#L180-L188)

**严重度:** 🔴 高危（数据一致性）

```python
def _resolve_today_plan(db, child_user_id, plan_date):
    plan = _get_plan_by_date(db, child_user_id, plan_date)
    if plan and is_plan_stale(plan, ...):
        return None          # ← 过期方案返回 None，但不删除！
    ...

def _get_plan_by_date(db, child_user_id, plan_date):
    return db.scalar(        # ← .scalar() 非确定性取一条
        select(TrainingPlan)
        .where(TrainingPlan.plan_date == plan_date)
    )
```

**链路分析:**

```
Day 1: 用户选时长 → 生成方案 plan(id=1, date=2026-07-06)
Day 2: _resolve_today_plan → is_plan_stale(id=1) = True → 返回 None
       但 plan(id=1) 仍留在 DB 中!
       create_plan_for_schedule → 创建 plan(id=2, date=2026-07-06)
       现在同一天有两条 plan 记录
       _get_plan_by_date → .scalar() → 随机返回 id=1 或 id=2
```

**影响:**

- 同一天出现多条 TrainingPlan 记录
- `_get_plan_by_date` 使用 `.scalar()` 非确定性取值
- 用户可能看到旧的过期方案内容而非新生成的方案
- 方案内容随机切换，难以排查

**修复方案:**

`_resolve_today_plan` 检测到过期方案时调用 `_delete_training_plan` 清理，或在 `_get_plan_by_date` 中加 `order_by` + `status != 'stale'` 过滤。

**修复难度:** 中（需确认清理逻辑不影响已有的打卡记录关联）

## P1 — 跨日训练窗口 API 判断缺陷

**文件:** [backend/app/services/training_service.py#L1609-L1611](../backend/app/services/training_service.py#L1609-L1611)

**严重度:** 🔴 高危（功能缺陷）

```python
# get_window_status（用户端调用的窗口状态 API）
def get_window_status(db, child_user_id, now=None):
    ...
    in_window = row.start_time <= current <= row.end_time
    #            ↑ 只处理普通窗口，没有跨日逻辑
```

同一文件中 `sync_media_exhausted_from_window` 已有正确的跨日处理：

```python
# sync_media_exhausted_from_window（内部判断，正确实现）
if row.start_time <= row.end_time:
    within = row.start_time <= current <= row.end_time
else:
    within = current >= row.start_time or current <= row.end_time  # 跨日
```

**影响:**

用户设置训练窗口 22:00→06:00（跨日）时：
- `get_window_status` API **永远返回 `in_window: false`**
- 凌晨训练的用户看到"不在训练窗口内"的误导状态
- 前端据此可能错误地阻止训练操作

**修复方案:**

将 `get_window_status` 的跨日判断逻辑与 `sync_media_exhausted_from_window` 对齐。

**修复难度:** 低（复用已有跨日逻辑，约 3 行改动）

## P2 — 归档操作无幂等性保护

**文件:**
- [backend/app/services/admin_service.py#L225-L231](../backend/app/services/admin_service.py#L225-L231)
- [backend/app/services/admin_service.py#L304-L310](../backend/app/services/admin_service.py#L304-L310)

**严重度:** 🟡 中危（运维安全）

```python
def delete_parent(db, admin_id, parent_id):
    parent = db.get(ChildUser, parent_id)
    if not parent or parent.role != auth_service.ROLE_PARENT:
        raise HTTPException(404, "家长不存在")
    _archive_parent_account(db, parent)  # ← 不检查是否已归档
    db.commit()
```

**问题:**

1. **误导性返回:** 对已归档账号重复调用，API 返回 `{"ok": True}`，调用方以为操作成功，实际什么都没做
2. **数据损坏风险:** `_archive_*_account` 内部的 `is_account_active` 守卫若被移除/绕过，会导致 `login_name` 被双重加前缀：`__deleted___deleted_123`
3. **profile_json 字段重复覆盖:** 归档字段每次覆盖写入，虽然目前值相同，但不是幂等的正确实现方式

**修复方案:**

```python
def delete_parent(db, admin_id, parent_id):
    parent = db.get(ChildUser, parent_id)
    if not parent or parent.role != auth_service.ROLE_PARENT:
        raise HTTPException(404, "家长不存在")
    if not auth_service.is_account_active(parent):
        raise HTTPException(410, "账号已归档")  # 明确告知已删除
    _archive_parent_account(db, parent)
    db.commit()
```

**修复难度:** 低（加状态检查，约 3 行改动）

## P2 — 管理员解绑后孩子静默变为不可登录

**文件:**
- [backend/app/services/admin_service.py#L342-L351](../backend/app/services/admin_service.py#L342-L351)
- [backend/app/services/auth_service.py#L135-L141](../backend/app/services/auth_service.py#L135-L141)

**严重度:** 🟡 中危（用户体验）

**链路:**

```
1. 管理员调用 unbind_child → 删除 ParentChildBind + 清除所有 session
2. 孩子失去唯一的家长绑定
3. login_student_by_password → has_active_parent_bind(db, user.id) → False
4. 返回 None → 孩子永远无法登录
```

```python
# auth_service.py
def login_student_by_password(...):
    if not has_active_parent_bind(db, user.id):
        return None  # ← 永久拒绝
```

**影响:**

- 管理员在后台解绑孩子时，**无任何警告或提示**
- 孩子账号静默变为不可用状态
- 除非管理员重新 bind 到另一个家长，否则永远无法恢复

**修复方案:**

- 解绑 API 响应中包含 `warning` 字段："孩子将无法登录，需重新绑定家长"
- 前端 `unbind_child` 操作前弹出二次确认对话框

**修复难度:** 低（后端加 warning 字段 + 前端加确认弹窗）
